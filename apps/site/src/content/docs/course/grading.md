本页是各 Lab 共用的参考。每个 Lab 的具体评分项写在各自的页面里。

## 概览

- 每个 Lab 都用课程的评测工具 `ldsdt` 自动评测。它装在你的实验仓库里（`ldsdt_kit/`），用 `uv run ldsdt <命令>` 调用。
- **需求、验收场景和评分依据全部公开。** 你在本地运行 `ldsdt grade` 得到的分数，就是成绩中的评测分。唯一的例外是 Lab 4 的「场景有效率」和「变异体击杀率」两项：计算它们需要课程组的参考实现，所以只在官方复评中计算，本地显示为「待复评」。
- 评测只检查你的系统在**运行目录**里留下的产物，不关心系统内部怎么实现。
- 计入成绩的是截止后助教的**官方复评**：助教用课程组自己的一份评测工具，对你提交的产物重新打分。修改你仓库里的评测代码不会影响成绩。

## 命令一览

在实验仓库根目录运行：

| 命令                                  | 作用                                                                                                  | 会不会调用模型           |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------ |
| `uv run ldsdt setup`                  | 生成 iCode 模型配置 `ldsdt-qwen`，同步智能体，检查环境。环境变量变了以后要重新运行                    | 只发一次很短的连通性请求 |
| `uv run ldsdt doctor`                 | 只检查环境                                                                                            | 同上                     |
| `uv run ldsdt sync`                   | 把 `agents/*.yaml` 复制到 iCode，名称加前缀 `ldsdt-`，并绑定 `ldsdt-qwen`。评测前会自动运行           | 否                       |
| `uv run ldsdt try <需求文档> --lab N` | 在任意一份需求上，按 Lab N 的要求运行系统并检查，**不计分**。产物在 `runs/try/<需求 id>/`，不会被提交 | 是                       |
| `uv run ldsdt grade labN`             | 在本 Lab 的计分需求上运行系统并打分                                                                   | 是                       |
| `uv run ldsdt submit labN`            | 门槛通过后提交运行产物，打标签 `labN-submit` 并推送                                                   | 否                       |
| `uv run ldsdt collect --week N`       | 打包在本仓库中使用 iCode、AiWork 的会话记录，用于第 N 次会话记录提交                                  | 否                       |

`grade` 的常用选项：

- `--task <需求 id>`：只运行指定的一份需求，可以重复使用。调试时很有用，但正式提交前要完整评测一次；
- `--no-run`：不运行系统，只对 `runs/labN/` 中已有的产物重新打分；
- `-v`：在终端显示每一项的问题和失败场景。

`try` 和 `grade` 一样可以加 `-v` 和 `--timeout <秒>`。

## 一次评测做了什么

运行 `uv run ldsdt grade labN` 时，评测工具依次：

1. 检查环境，并同步 `agents/` 下的智能体；
2. 对本 Lab 的每一份计分需求：
   - 清空并建立运行目录 `runs/labN/<需求 id>/`，把需求文档复制为其中的 `input.md`；
   - 启动你的工作流 `ldsdt`，输入为：

     ```json
     {"requirement": "<input.md 的绝对路径>", "run_dir": "<运行目录的绝对路径>", "lab": N}
     ```

   - 工作流结束（或超时）后，在运行目录里写入 `run.json`，记录结果、用时、会话编号和 token 用量；
3. 按本 Lab 的评分项检查各运行目录中的产物，结果写入 `runs/labN/grade.json`，并追加一行到 `.ldsdt/grade-history.jsonl`。

`lab` 告诉你的工作流这次需要哪些产物。每个 Lab 运行的都是**到本 Lab 为止的完整系统**，例如 Lab 3 会依次运行需求分析、设计和实现三个模块，前面模块的产物每次都会重新生成。

### 运行目录

```text
runs/labN/<需求 id>/
├─ input.md     需求文档的副本
├─ warmup/      Lab 0 的产物
├─ spec/        需求分析模块的产物（Lab 1 起）
├─ design/      设计模块的产物（Lab 2 起）
├─ repo/        实现模块生成的目标仓库（Lab 3 起）
├─ tests/       测试模块的产物（Lab 4 起）
└─ run.json     评测工具写入的运行记录
```

各目录中具体要有哪些文件、是什么格式，见各 Lab 页面的「固定要求」。

### 计分需求

| Lab     | 计分需求               | 位置              |
| ------- | ---------------------- | ----------------- |
| Lab 0   | `todo-cli`、`wordstat` | `tasks/practice/` |
| Lab 1–4 | `library`、`timesheet` | `tasks/public/`   |

`tasks/practice/` 下还有其他练习需求，规模都比较小，适合用 `ldsdt try` 调试。

### 时长上限

每份需求的单次运行有时长上限，到时会被终止：

| Lab   | 运行的模块                          | 上限    |
| ----- | ----------------------------------- | ------- |
| Lab 0 | 热身工作流                          | 10 分钟 |
| Lab 1 | 需求分析                            | 15 分钟 |
| Lab 2 | 需求分析 → 设计                     | 25 分钟 |
| Lab 3 | 需求分析 → 设计 → 实现              | 45 分钟 |
| Lab 4 | 需求分析 → 设计 → 实现 → 测试与修复 | 90 分钟 |

**超时或出错不会直接判 0**：评测工具照常检查运行目录中已经生成的产物。所以，让系统尽早把能确定的产物写到磁盘上，是值得的。

一次 `grade` 要依次运行两份需求。按课程组参考系统的实测，Lab 1–2 约半小时以内，Lab 3 约 1 小时，Lab 4 约 2 小时。日常调试请先用 `ldsdt try` 和 `--task`，不要每改一次就完整评测。

## 门槛与评分

### 门槛

满足以下两点，评测分才有效，`submit` 也才允许提交：

1. 工作流能被 iCode 加载（`doctor` 中「工作流 ldsdt」一项通过）；
2. 在本 Lab 的每一份计分需求上都启动过运行（每个运行目录里都有 `run.json`）。

不满足门槛时，本 Lab 评测分为 0。

### 评分的组成

每个 Lab 满分 100，由两类评分项组成：

- **每份需求的评分项**：分别在每份计分需求的产物上计算，再取平均；
- **仓库级评分项**：从 Lab 1 起有一项 `design-choices.yaml`（10 分），见下文。Lab 0 的仓库级评分项是环境检查和会话收集。

从 Lab 2 起，每份需求的评分项中有一项「**前序模块**」：把前面各 Lab 中模块产物的评分项按原权重折算后计入。这保证了在后面的 Lab 里，前面的模块仍然要正常工作。

各 Lab 的具体评分项见各自的页面。

### `design-choices.yaml`

每个 Lab（Lab 1 起）都留有一组设计选择（例如「规约用什么格式表示」「失败后如何重试」），在 Lab 页面的「可选设计空间」中列出。A、B 商定后，把本 Lab 每个维度的选择和理由写进仓库根目录的 `design-choices.yaml`：

```yaml
lab1:
  D1.1: # 规约语言
    choice: 'JSON 结构化模式'
    note: '便于后面的设计模块直接读取字段'
```

- 本地评测只检查本 Lab 的每个 `choice` 是否填写；
- 官方复评还会检查 A、B 两个仓库中的这份文件是否一致；
- `choice` 可以是 Lab 页面列出的示例，也可以是你们自己的方案。

### 换算到成绩

- 每个 Lab 的评测分（满分 100）换算为该 Lab 成绩中的 **6 分**，取 A、B 两个仓库的平均，小组共享；
- 另外 **4 分**是验收问答，个人计分；
- 每个 Lab 占总成绩的 10%。

## 提交

### 流程

1. 运行 `uv run ldsdt grade labN`，确认门槛通过、分数满意；
2. 运行 `uv run ldsdt submit labN`。它会：
   - 确认本 Lab 已有评测结果并且门槛通过；
   - 检查待提交的文件里有没有 API Key，发现时拒绝提交并列出文件；
   - 把全部改动（包括 `runs/labN/`）提交为一次 commit，打上标签 `labN-submit`，推送到你的仓库。

截止前可以重复评测和提交，**以截止时间点上最后一次推送的 `labN-submit` 标签为准**。

:::caution
`submit` 会提交仓库中的**全部**改动。提交前用 `git status` 看一眼，确认没有不该提交的文件。
:::

### 会话记录

A、B 每次提交仓库时，还要把自己的会话记录上传到「学在浙大」。截止时间与同一天的仓库提交相同：

| 次序 | 学在浙大作业 | 截止                    | 同一天截止的仓库提交 |
| ---- | ------------ | ----------------------- | -------------------- |
| 1    | 会话记录 1   | 11 月 26 日 23:59       | Lab 0                |
| 2    | 会话记录 2   | 12 月 3 日 23:59        | Lab 1                |
| 3    | 会话记录 3   | 12 月 10 日 23:59       | Lab 2                |
| 4    | 会话记录 4   | 12 月 17 日 23:59       | Lab 3                |
| 5    | 会话记录 5   | 12 月 24 日 23:59       | Lab 4                |
| 6    | 会话记录 6   | 2027 年 1 月 6 日 23:59 | 期末项目             |

第 N 次提交时，在仓库根目录运行：

```bash
uv run ldsdt collect --week N
```

它把你在本仓库中使用 iCode、AiWork 的会话打包为 `.ldsdt/collect/week-N-<个人编号>.zip`，把这个文件上传到学在浙大对应的作业即可。

- 运行时会列出找到的会话，你可以排除与课程无关的会话。每次打包的都是到当时为止的全部会话，所以即使某次漏交，下一次也会补上。
- 压缩包里有你与 AI 工具的完整对话。它只上传到学在浙大，**不要提交到 Git 仓库**（仓库已设置为忽略它），也不要发给其他同学。
- 已知的 API Key 会在打包时被替换掉。
- 如果 AiWork 的会话一个都没有找到，通常是因为没有在 AiWork「编码」页的「项目」中打开本仓库，见 [Lab 0 第 6 步](../../labs/lab-0/#6-配置你的辅助开发工具)。

### 迟交

每迟交 24 小时，该 Lab 的评测分乘以 0.9，最多迟交 3 天。如果是模型服务故障或 Key 问题导致的延误，凭 `grade-history.jsonl` 和 `run.json` 中的报错，可以联系助教申请免责。

## 官方复评与抽查

- **官方复评**：截止后，助教拉取每个仓库的 `labN-submit` 标签，用课程组的评测工具副本对 `runs/labN/` 中的产物重新打分，不重新运行你的系统。Lab 4 的「场景有效率」和「变异体击杀率」在这一步计算。
- **抽查复跑**：每个 Lab 随机抽 3 组，助教在自己的电脑上重新运行你提交时的系统，与你提交的产物对比。模型输出有随机性，不要求完全一致；差距过大的会进入人工审查。
- **核对运行记录**：`run.json` 记录了每次运行的 iCode 会话编号，可以与 `collect` 收集的本地会话记录相互核对。

## 规则

- **产物必须由系统生成**。不得手工修改运行目录中的任何产物（规约、设计、目标仓库、测试）后当作系统的输出提交。可以多次运行、改进系统，然后提交满意的一次。
- **系统运行时不得读取评分依据**：例如 `tasks/` 下的接口目录（`*.interface.json`）、练习需求的参考实现和变异体。也不得在提示词里写入只针对某份计分需求的内容（例如照抄它的验收场景）。系统应当对任何一份同样格式的需求都能工作。
- **不得修改评测工具**（`ldsdt_kit/`）来改变分数。官方复评用的是课程组的副本，修改不会生效；`submit` 会记录评测工具的指纹，发现改动时提示。
- 违反以上规则，一经查实，该 Lab 评测分记为 0。

## 期末项目

期末项目的评测方式与 Lab 不同：没有本地评测分，由助教在截止后安装各组系统生成的仓库，运行你们需求中的验收场景和助教补充的场景。详见[期末项目](../../labs/final/)。

## 获取课程更新

每个 Lab 发布时，评测工具、新的需求和说明可能会更新。开始新 Lab 前，在仓库根目录运行：

```bash
git pull upstream main
uv sync
```

如果出现合并冲突，通常是因为你改过 `ldsdt_kit/` 或 `tasks/` 下的文件。这些目录只应由课程更新，请保留课程的版本。
