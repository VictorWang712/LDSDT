## 目标

Lab 0–4 中，你们的系统一直在课程给定的需求上运行。期末项目中，每组**自己设计一个项目**，把它写成本课程格式的需求文档，交给本组的系统，让系统生成一个可以安装使用的代码仓库。

- **技术汇报**侧重你们的**系统设计**：各模块怎样设计、为什么这样设计、在自己的项目上暴露了什么问题。
- **现场演示**侧重系统**生成的仓库**：它能不能按 README 装好，能不能正确完成指定的操作。

## 设计你们的项目

每组设计**一份**需求。A、B 两套系统都在这份需求上运行。

需求文档可以用辅助开发工具协助编写（A 用 AiWork，B 用 iCode），但要遵守下面的约束。

### 格式

与 `tasks/public/` 下的需求相同：开头的 YAML 头、编号的功能需求（`FR-xxx`）、规则（`R-xxx`）和 YAML 格式的验收场景。动手前请先仔细读一遍 `library.md` 或 `timesheet.md`，照着它们的结构写。

### 环境不能超出课程的公开需求

- Python 3.12 命令行程序，**只用标准库**；
- 数据存放在当前目录下的文件中；
- 不联网，没有图形界面，没有多线程、多进程；
- **输出必须是确定的**：同样的命令和数据，每次输出都一样。不要依赖当前日期时间或随机数；确实需要时，让它们作为命令参数传入（例如 `--date 2026-12-01`）。否则你们自己写的验收场景也无法稳定通过。

### 规模

| 项             | 要求                                  |
| -------------- | ------------------------------------- |
| 功能需求（FR） | 12–25 条                              |
| 规则（R）      | 至少 3 条                             |
| 验收场景       | 20–60 个，每条 FR 至少被 1 个场景覆盖 |

下限与 `timesheet`（15 条 FR、22 个场景）相当；上限是为了让系统能在 90 分钟内完成一次运行。

### 原创

不得与课程中出现过的需求雷同，包括 `library`、`timesheet`，以及 `tasks/practice/` 下的各练习需求。

:::tip[怎样设计一份「好」需求]

- **规则要写清楚**：错误信息的原文、退出码、多个错误同时出现时先报哪一个、排序与并列怎样处理、数字怎样舍入。含糊的地方，系统和你们的验收场景很可能理解得不一样。
- **场景要和需求一致**：每个验收场景的期望输出，都应当能从需求文字中推出来。
- **有一定的业务规则**：状态的累积、跨实体的约束、统计与汇总，比单纯的增删查改更能体现你们系统的能力。
  :::

## 运行系统

截止前，你们可以反复改进系统、修改需求、多次运行。但最终提交的生成仓库必须满足：

- 是**提交的系统版本**在**提交的需求**上**完整运行一次**的结果；
- **未经任何手工修改**。

这和平时的 Lab 一样：课程组会用 `run.json` 中的会话编号与 `collect` 收集的记录核对，并随机抽查复跑。手工修改生成的仓库，按学术诚信规则处理。

## 提交内容

1 月 6 日 23:59 前，每个系统仓库（`<组号>-aiwork`、`<组号>-icode`）各自提交：

1. **系统本身**：工作流、智能体配置、`design-choices.yaml` 等，即你们的系统仓库；
2. **本组的需求文档**：`final/requirement.md`，A、B 两个仓库中的这份文件必须相同；
3. **生成的仓库与运行记录**：本系统在这份需求上运行一次得到的仓库，以及 `run.json`。

此外，每组提交一份**技术报告**。

整理与提交由 `ldsdt final` 命令完成，具体用法随期末任务发布。

## 评分

期末项目占总成绩的 20%，现场演示另占 10%。

### 期末交付（12 分）

A、B 两个系统生成的仓库分别评分，再取平均。

| 项                       | 分值 | 怎么评                                                                   |
| ------------------------ | ---- | ------------------------------------------------------------------------ |
| 需求文档：格式合规       | 1    | `ldsdt check-req` 通过                                                   |
| 需求文档：规模与清晰度   | 2    | 助教按评分表评：规模在要求范围内，规则明确、没有矛盾，场景与功能需求对应 |
| 生成的仓库：本组验收场景 | 3    | 助教在干净的环境中安装生成的仓库，运行你们需求中的验收场景，按通过率计分 |
| 生成的仓库：补充场景     | 4    | 截止后，助教根据你们的需求文字补写约 10 个场景（不公开），按通过率计分   |
| 生成的仓库：跨平台       | 2    | 在 macOS 和 Windows 上都能按 README 安装运行                             |

「补充场景」的期望输出只依据你们需求文档中写明的内容。需求写得越清楚，系统越容易做对，补充场景也越不会出现分歧。

### 技术报告（8 分）

使用统一模板（随期末任务发布），侧重系统设计：

- 每个模块的设计选择、理由与实现方式；
- 各模块产物中典型的问题，以及在自己的项目上运行时暴露的问题；
- 两套系统的差异，以及 A、B 使用 AI 工具的对比（由 C 主笔）。

### 技术汇报与现场演示（总成绩的 10%）

1 月 7 日课上，每组：

1. 简要汇报系统设计；
2. 助教从你们的两个生成仓库中**随机选一个**，现场从 GitHub clone 对应的系统仓库，进入其中 `final/` 下生成的仓库，按它的 README 安装；
3. 演示助教根据你们的需求当场指定的 3 个操作；
4. 回答关于系统设计的提问。
