## 目标

从本 Lab 开始，你们一个模块一个模块地搭建系统。本 Lab 构建**需求分析模块**：读入一份需求文档，产出三样东西：

- **结构化规约**：把每条功能需求整理成后面的模块容易使用的形式；
- **接口目录**：程序有哪些命令、各自的参数与选项，以及会报出哪些错误；
- **功能切片**：把全部功能需求分成若干组，并给出组与组之间的依赖，为后面的设计与实现做准备。

## 背景知识

### 为什么不把需求文档直接交给写代码的智能体

需求文档是写给人看的：同一条规则可能分散在好几处，错误信息、退出码、排序与并列、舍入方式等细节夹在大段文字里，还会有没写清楚的地方。直接交给一个智能体「照着写代码」，它很容易漏掉细节，或者每次理解得不一样。

需求分析模块的作用，是先把这些内容整理成**明确、完整、便于后续模块查找**的形式：

- **规约**回答「每条功能需求到底要求什么」；
- **接口目录**回答「程序对外长什么样」。它是后面设计、实现、测试各模块共同的依据；
- **切片**回答「这些功能可以怎样分批实现」。

## 固定要求

评测时，工作流收到的输入中 `lab` 为 `1`。运行结束后，运行目录的 `spec/` 下必须有以下三个文件。除此之外，`spec/` 下可以放任何你需要的文件，例如规约正文。

### `spec/index.json`：规约索引与切片

```json
{
  "requirement_id": "library",
  "items": [{ "fr": "FR-001", "spec_ids": ["S-001"], "files": ["spec/readers.md"] }],
  "assumptions": [{ "id": "ASM-1", "text": "……", "related": ["FR-011"] }],
  "slices": [
    { "id": "readers", "frs": ["FR-001", "FR-002"], "depends_on": [] },
    { "id": "borrowing", "frs": ["FR-011", "FR-012"], "depends_on": ["readers"] }
  ]
}
```

| 字段          | 要求                                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `items`       | 每条 FR 一项：`fr` 是 FR 编号；`spec_ids` 是这条 FR 对应的规约条目编号，非空；`files` 是规约正文所在的文件，路径**相对于运行目录**（如 `spec/readers.md`），文件必须存在 |
| `assumptions` | 需求没有写清楚、你的系统做出的假设，每项有 `id` 和 `text`，`related` 可选。没有假设时写空数组 `[]`                                                                       |
| `slices`      | 功能切片，非空。每条 FR **恰好**属于一个切片；`depends_on` 只能指向已有的切片，且不能有环                                                                                |

规约编号、文件怎么拆分、正文写成什么样，都由你决定。

### `spec/interface.json`：接口目录

```json
{
  "commands": [
    {
      "name": "reader add",
      "args": ["证号", "姓名"],
      "options": ["--type"],
      "frs": ["FR-001"]
    }
  ],
  "errors": [
    {
      "command": "*",
      "message": "error: invalid date <原值>",
      "exit": 2,
      "frs": ["R-001"]
    },
    {
      "command": "borrow",
      "message": "error: reader <证号> is suspended",
      "exit": 4,
      "frs": ["FR-011"]
    }
  ]
}
```

| 字段       | 要求                                                                                                                                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `commands` | 每个子命令一项。`name` 是命令名，不含程序名（写 `reader add`，不写 `lib reader add`）；`args` 是位置参数，按顺序，名字随意；`options` 是选项，写选项名即可（如 `--type`）；`frs` 是相关的需求编号  |
| `errors`   | 需求中**明确写出的**错误。`message` 是错误信息原文，其中会变化的部分用 `<...>` 占位，占位符的名字随意；`exit` 是退出码；`command` 是所属命令，适用于所有命令时写 `*`；`frs` 是相关的需求或规则编号 |

只列以**非零退出码**结束的错误。下面这些不要列：

- 退出码为 0 的逐行报告或警告，例如导入时跳过某一行的提示；
- 需求没有写出原文的错误，例如命令行参数解析库自动给出的用法错误提示。

### `spec/FORMAT.md`：规约格式说明

用文字说明你们的规约正文采用什么格式：有哪些部分、每部分写什么、后面的模块应当怎样读取。后面的设计模块会依赖这份说明。

### 可选：`validators/spec.py`

你可以在**仓库根目录**（不是运行目录）提供一个脚本 `validators/spec.py`，检查本次运行的规约正文是否符合 `FORMAT.md` 中声明的格式。评测时这样调用它：

```bash
python validators/spec.py <运行目录>/spec
```

退出码为 0 表示通过。脚本只能用 Python 标准库和 PyYAML，同样**不能导入课程工具包** `ldsdt_kit`。验收问答中可能会请你讲解它检查了什么。

## 可选设计空间

下面每个维度都由你们自己选择，表中的方案只是示例，也可以用自己的方案。A、B 商定后，把选择和理由写进 `design-choices.yaml` 的 `lab1` 一节（见[评测与提交](../../course/grading/#design-choicesyaml)）。

| 维度                | 示例方案                                                                                     | 可以考虑的权衡                                                                                                               |
| ------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| D1.1 规约语言       | JSON/YAML 结构化模式；Given-When-Then 场景式；输入-输出表；前置/后置条件；用户故事加验收条件 | 结构化程度越高，后面的模块越容易精确读取，但写起来更容易漏掉「说明性」的细节；越接近自然语言，越容易保留语义，但难以自动检查 |
| D1.2 生成策略       | 一次生成全部；先抽取要点再精炼；按需求章节分块生成后合并；生成者加评审者                     | 一次生成最简单，但需求长时容易遗漏；分块能减少遗漏，但要处理块与块之间的重复和不一致；评审能发现问题，但多花时间和 token     |
| D1.3 分解方式       | 按需求章节；按数据实体；按用户操作流程；交给智能体聚类                                       | 切片会影响后面的设计与实现顺序。按实体切分通常依赖清楚；按流程切分更贴近使用场景，但可能有交叉                               |
| D1.4 校验           | 不校验；自己写格式与覆盖检查（不能调用课程工具包）；校验失败时反馈给智能体重做               | 校验与重做能明显减少格式错误，但会增加运行时间，要注意 15 分钟的时长上限                                                     |
| D1.5 歧义与规则复用 | 忽略；显式列出假设并采用保守的解释；把「规则」一节展开到每个引用它的规约条目                 | 展开规则让每个条目自成一体，便于后面单独使用，但会让规约变长；集中写一次更简洁，但后面的模块要自己去查                       |

1. **读需求，定方案**：A、B 一起读 `library.md` 和 `timesheet.md`，讨论上面的五个维度，记下选择。
2. **写智能体与工作流**：在 `agents/` 下写需求分析用的智能体配置，修改 `.chrys/workflows/ldsdt/ldsdt.py`，让工作流在 `lab` 为 1 时产出上面三个文件。工作流的写法见模版仓库的 `docs/icode-workflow-cheatsheet.md`。
3. **在工作流里自查（可选）**：系统不能调用课程工具包，校验要自己写，例如在智能体节点后接一个 Python 节点，检查三个文件是否存在、JSON 能否解析、FR 是否都被覆盖，发现问题就反馈给智能体重做。在工作流外，可以用下一步的 `ldsdt try -v` 查看评测工具发现的问题。

4. **先在小需求上调试**：练习需求 `todo-cli` 和 `wordstat` 也附带了课程组的接口目录（只有命令部分），可以先用它们调试，几分钟就能跑完：

   ```bash
   uv run ldsdt try tasks/practice/todo-cli.md --lab 1 -v
   ```

5. **在计分需求上评测**：

   ```bash
   uv run ldsdt grade lab1 -v
   ```

   每份需求限时 15 分钟。结果中会列出接口目录**漏掉的**和**多出的**命令与错误，据此改进你的系统。

:::caution[不要让系统读取评分依据]
`tasks/public/` 下的 `library.interface.json`、`timesheet.interface.json` 是评分用的课程组接口目录，它们是公开的，你可以阅读它们，对照检查系统的产物。但**系统运行时不得读取它们**，也不得在提示词里写入针对某份需求的内容。期末你们的系统要在自己设计的需求上运行，那时没有这样的文件。
:::

:::danger[需求理解必须由智能体完成]
本 Lab 考察的是**智能体**整理需求的能力。命令、参数、选项、错误信息和退出码，以及规约正文，必须由智能体阅读需求后写出。工作流中的 Python 节点只能做下面这些事：

- 从需求中提取 FR 编号和 YAML 头；
- 检查产物的格式与覆盖情况，把问题反馈给智能体；
- 合并多个智能体的输出，写入文件。

不允许用正则表达式或其他规则代码，从需求中直接抽取命令、选项、错误信息或退出码，再让智能体「审校」。验收问答时我们会看工作流代码。违反这一条的，「接口目录：命令」和「接口目录：错误」两项记 0 分。
:::

## 评分

**门槛**：工作流能加载，系统没有引用课程工具包（`doctor` 中「系统不调用评测工具」通过），并在 `library` 和 `timesheet` 上都启动了运行。

| 评分项                | 分值 | 说明                                                                              |
| --------------------- | ---- | --------------------------------------------------------------------------------- |
| `index.json` 合法     | 10   | 字段齐全，引用的文件都存在，覆盖全部 FR。有任何一处问题即为 0                     |
| FR 覆盖与切片         | 15   | FR 覆盖率 × 7.5，加上切片合法 7.5（每条 FR 恰好属于一个切片、依赖都存在、无环）   |
| 接口目录：命令        | 25   | 与课程组接口目录比对，见下文                                                      |
| 接口目录：错误        | 30   | 与课程组接口目录比对，见下文                                                      |
| 格式说明              | 10   | `spec/FORMAT.md` 存在 5；提供 `validators/spec.py` 且对本次产物退出码为 0，再得 5 |
| `design-choices.yaml` | 10   | 本 Lab 的五个维度都已填写（仓库级）；官方复评还会检查 A、B 两份是否一致           |

前五项在两份需求上分别计算，再取平均。如果接口目录不是由智能体写出的（见上文「需求理解必须由智能体完成」），验收时把两项接口目录的分数改为 0。评测工具不会自动判定这一点。

### 接口目录怎样比对

**命令**（25 分）：

- 比较命令名时去掉程序名、合并多余的空白，例如 `lib  reader add` 与 `reader add` 视为相同；
- 选项只看选项名，`--type student|staff` 记为 `--type`，忽略 `--help`；
- 得分 = 0.5 × 命令名的 F1 + 0.5 × 参数个数与选项集合都正确的命令数 / 课程组的命令数。

**错误**（30 分）：

- 一条错误由「错误信息 + 退出码」确定，不看 `command` 字段，因为同一个错误常被多条命令共用；
- `<...>` 是占位符，可以匹配任意文字。两条信息只要有一方能匹配另一方，就视为同一条错误。例如 `error: reader <证号> not found` 与 `error: reader <id> not found` 相同；
- 去掉占位符和 `error:` 之后不足 3 个字符的信息（如 `error: <说明>`）太笼统，不能当作通配，只能逐字匹配；
- `exit` 为 0 的条目不参与比对；
- 得分为 F1：漏掉课程组目录中的错误会降低召回率，多列需求中没有写出的错误会降低准确率。

**F1** 是准确率与召回率的调和平均：准确率 = 你列出的条目中正确的比例，召回率 = 课程组的条目中被你列出的比例。

## 常见问题

### 接口目录里应该写需求里的哪些错误

需求中写出了错误信息原文的都要写，包括「规则」一节中适用于所有命令的错误（如非法日期、非法编号）。同一类错误在不同条件下文字不同时（例如 `error: empty name` 和 `error: empty title`），可以分别列出，也可以写成一条带占位符的 `error: empty <字段>`，两种写法都能匹配。

### `index.json` 合法这一项为什么是 0

这一项要求完全没有问题。运行 `uv run ldsdt grade lab1 -v` 或 `uv run ldsdt try <需求文档> --lab 1 -v` 查看具体问题。最常见的原因是 `files` 中的路径没有相对于运行目录（应写 `spec/xxx.md`），或者漏掉了某条 FR。

### 运行超过了 15 分钟

需求分析一般用不了这么久。常见原因是智能体反复重写很长的规约文件，或者校验与重做的循环没有上限。可以限制重做的轮数，让每个智能体的任务更小，或者把提取 FR 编号、合并与写文件这类机械工作交给 Python 节点（命令、错误等内容仍要由智能体写出，见「需求理解必须由智能体完成」）。

实践中比较稳定的做法是让智能体**只回复 JSON**、由 Python 节点写文件，而不是让智能体自己用工具写很长的文件。这样单份需求一般 5 分钟以内就能完成。

更多问题见[常见问题](../../course/faq/)。
