## 目标

本 Lab 在需求分析模块之后接上**设计模块**。设计模块读入上一个模块产出的规约与接口目录，为目标程序做出一份设计：

- **模块划分**：程序分成哪些模块（Python 文件），每个模块负责什么；
- **接口**：每个模块对外提供哪些函数和类，签名是什么；
- **依赖**：模块之间谁调用谁；
- **追溯**：每条功能需求、每个命令由哪些接口负责；
- **实现计划**：分成哪些实现任务，按什么顺序做。

下一个 Lab 的实现模块会按这份设计写代码，评测也会检查代码是否与设计一致。

## 背景知识

### 为什么要单独做设计

`library` 有 25 条功能需求、二十多个命令，涉及读者、馆藏、借还、预约、罚款、导入导出等子系统，它们之间又有交叉的规则（例如停借的读者不能借书，也不能预约）。直接让一个智能体「写出整个程序」，常见的问题是：

- 同一条规则在几个命令里各写一遍，写得不一样；
- 文件越写越长，后写的部分忘了前面定下的数据格式；
- 出了错不知道该改哪里。

设计模块先把程序**拆开**，再把需求**分配**到拆开后的各部分上：

- 模块划分与依赖决定了代码的结构，依赖无环意味着可以自底向上地实现和测试；
- 接口签名是模块之间的约定，实现时各部分只需要遵守签名，可以分开写；
- 追溯关系让每条需求都有明确的负责人，检查遗漏、定位缺陷都靠它；
- 实现计划把上面这些变成一个个可以单独交给智能体的小任务，这正是下一个 Lab 要用的。

### 设计的产物给谁用

设计的读者是**下一个模块**，不是人。设计写得再漂亮，实现模块读不懂、用不上，也没有意义。所以动手之前，先想清楚你们打算在 Lab 3 中怎样实现：一次生成整个仓库，还是按计划逐个任务生成？每个任务给智能体看哪些内容？这些决定会影响设计应该细到什么程度。

## 固定要求

评测时，工作流收到的输入中 `lab` 为 `2`。系统要**先运行需求分析模块**，产出与 Lab 1 相同的 `spec/`，再运行设计模块。运行结束后，运行目录的 `design/` 下必须有 `manifest.json`。`design/` 下还可以放其他设计文件（如设计说明、类图），格式自定。

### `design/manifest.json`

```json
{
  "modules": [
    { "name": "store", "path": "lib/store.py", "responsibility": "读写数据文件" },
    { "name": "readers", "path": "lib/readers.py", "responsibility": "读者的增改查与停借" },
    {
      "name": "cli",
      "path": "lib/__main__.py",
      "responsibility": "解析命令行，调用各模块，输出结果"
    }
  ],
  "interfaces": [
    { "module": "store", "signature": "def load(path: Path) -> dict" },
    { "module": "store", "signature": "def save(path: Path, db: dict) -> None" },
    {
      "module": "readers",
      "signature": "def add_reader(db: dict, reader_id: str, name: str, kind: str) -> None"
    },
    { "module": "readers", "signature": "class ReaderError(Exception)" },
    { "module": "cli", "signature": "def main(argv: list[str] | None = None) -> int" }
  ],
  "dependencies": [
    { "from": "cli", "to": "readers" },
    { "from": "cli", "to": "store" }
  ],
  "trace": [
    { "fr": "FR-001", "interfaces": ["readers.add_reader", "cli.main"] },
    { "command": "reader add", "interfaces": ["readers.add_reader"] }
  ],
  "plan": [
    { "id": "T1", "module": "store", "frs": ["FR-007"], "depends_on": [] },
    { "id": "T2", "module": "readers", "frs": ["FR-001", "FR-002"], "depends_on": ["T1"] },
    { "id": "T3", "module": "cli", "frs": ["FR-001"], "depends_on": ["T2"] }
  ]
}
```

上面只是格式示例，不是 `library` 的参考设计。各字段的要求：

| 字段           | 每项的字段                                                                                     | 要求                                                                                                                                                                                         |
| -------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `modules`      | `name`、`path`、`responsibility`（均为字符串）                                                 | 非空。`path` 是模块文件**相对于目标仓库根目录**的路径，以 `.py` 结尾，不含 `..`，各模块互不相同。一个模块对应一个文件                                                                        |
| `interfaces`   | `module`（模块名）、`signature`（字符串）                                                      | `signature` 是**一行** Python 函数头或类头，不含冒号后的内容，例如 `def borrow(db: dict, reader: str, book: str) -> None`、`class Loan`。只写模块**顶层**的函数和类，不写类的方法            |
| `dependencies` | `from`、`to`（模块名）                                                                         | `from` 依赖（导入、调用）`to`。只能引用已声明的模块，不能有环。模块多于一个时，每个模块都要出现在至少一条依赖边上                                                                            |
| `trace`        | `fr` 或 `command`（字符串，二选一），`interfaces`（字符串数组）                                | 每条 FR、每个命令都要有一项。`interfaces` 中的每个引用写成「模块名.函数名」或「模块名.类名」，如 `readers.add_reader`。`command` 写命令名，不含程序名，与 `spec/interface.json` 中的写法相同 |
| `plan`         | `id`（字符串）、`module`（模块名）、`frs`、`depends_on`（字符串数组，`depends_on` 是任务编号） | 任务编号唯一；`depends_on` 只能指向已有任务，不能有环。全部任务合起来要覆盖全部模块与全部 FR                                                                                                 |

除这五个字段外，你可以在 `manifest.json` 中加任何字段（例如给接口加 `doc`、给任务加 `description`），评测会忽略它们。

### 下一个 Lab 会怎样使用这份设计

Lab 3 评测「设计一致性」时，会检查：

- `modules` 中每个模块的 `path` 在目标仓库中存在；
- `interfaces` 中的每个函数，在对应模块文件的**顶层**以相同的名字和相同的参数个数定义；每个类以相同的名字定义。参数个数包括普通参数和仅限关键字参数，不包括 `*args` 和 `**kwargs`，有默认值的参数也算。

所以设计中的签名不是随便写写的：它们就是实现时要遵守的约定。签名列得太多太细，实现时容易对不上；列得太少，设计又起不到约束作用。

| D2.5 设计模块的内部编排 | 单个智能体；主智能体加子智能体（`sub_agents`）；工作流中的并行节点加 `wf.join`；设计者加评审者                                        | 拆开能让每个智能体的任务更小，但各部分之间的接口要有人统一；评审能发现问题，但多一轮运行                                                                |
| D2.6 校验与回环         | 不校验；自己写结构检查（不能调用课程工具包）；校验失败时用 `wf.loop` 把问题反馈给智能体重做                                           | 结构检查（字段、追溯、依赖有环、签名能否解析）用标准库就能写，能挡住大部分格式错误；要给重做设上限，注意 25 分钟的时长上限                              |

- 读取文件，把内容交给智能体；
- 检查产物的格式与一致性，把问题反馈给智能体；
- 合并多个智能体的输出，写入文件。

不允许用规则代码从接口目录直接生成设计（例如「每个命令生成一个函数」「每个切片生成一个模块」「把 `interface.json` 中的 `frs` 直接抄成 `trace`」），再让智能体「审校」。验收问答时我们会看工作流代码。违反这一条的，「可追溯」「结构合理」「签名可解析」三项记 0 分。Lab 1 中「需求理解必须由智能体完成」的规定继续有效。
:::

几点说明：

- **追溯对照的是课程组的接口目录**，不是你们自己的 `spec/interface.json`。如果需求分析模块漏掉了某个命令，设计模块通常也不会追溯它，这一项会因此丢分。命令名的比较方式与 Lab 1 相同：去掉程序名，合并多余的空白。
- **接口引用要写成「模块名.名字」**，其中模块名是 `modules` 中的 `name`，不是文件路径；名字是签名中的函数名或类名。`trace` 中引用了没有声明的接口，这个引用不算数。
- 违反「设计必须由智能体完成」的，验收时把三项改为 0；违反 Lab 1「需求理解必须由智能体完成」的，前序模块中两项接口目录的分数改为 0。评测工具不会自动判定这两点。

## 常见问题

### 「清单格式」为什么是 0

这一项要求完全没有问题。运行 `uv run ldsdt grade lab2 -v` 查看具体是哪一项。常见原因：

- `trace` 中某项既没有 `fr` 也没有 `command`，或者 `interfaces` 写成了字符串而不是数组；
- `plan` 中某个任务没有 `depends_on`，没有依赖时要写空数组 `[]`；
- `frs` 写成了逗号分隔的字符串。

### 签名应该写成什么样

一行就能被 Python 解析的函数头或类头。评测会在签名后面补上 `: ...` 再解析，所以末尾写不写冒号都可以。下面这些都可以：

```text
def borrow(db: dict, reader: str, book: str, day: date) -> Loan
async def fetch(url: str) -> bytes
class Loan
class LibraryError(Exception):
```

下面这些不行：`borrow(db, reader, book)`（缺少 `def`）、`def Loan.renew(self)`（类的方法不能单独列出）、`def f(x) -> int: return x`（带了函数体）。

### 只有一个模块行不行

格式上允许：只有一个模块时不检查孤立模块。但这样的设计对实现几乎没有约束，所有代码都挤在一个文件里，Lab 3 中也很难按计划逐步实现。验收问答时我们会请你说明划分模块的理由。

### 运行超过了 25 分钟

25 分钟包括需求分析模块。Lab 1 中运行较慢的系统，可以先把需求分析模块的时间压下来。设计模块本身常见的问题与 Lab 1 类似：让智能体反复改写一个很长的 `manifest.json`，或者重做的循环没有上限。可以让智能体只回复 JSON，由 Python 节点写文件，并把重做限制在一两轮。

更多问题见[常见问题](../../course/faq/)。
