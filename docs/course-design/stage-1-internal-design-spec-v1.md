- 课程：LLM-Driven Software Development and Testing
- 阶段：阶段一——国产大模型在国产算力平台上的部署
- 文档性质：课程团队内部设计基线
- 版本：1.0
- 状态：待课程团队评审
- 最后更新：2026-08-04

## 1. 文档目的

本文档冻结阶段一实验的平台无关设计，包括教学目标、责任边界、学生自由度、交付物、课堂组织、一周验收流程、自动评测结论和后续建设任务。

本文档不是学生实验讲义，也不包含尚未确定的服务器命令。学生讲义、协议 Schema、Starter Kit、公开测试和正式评测器必须由本文档派生，并保持一致。

本文使用以下约定：

- **必须**：构成阶段一通过条件，不满足即不能签发阶段一凭证；
- **应当**：原则上需要满足，只有明确理由时才能偏离；
- **可以**：允许的实现选择，不构成统一要求；
- **待定**：依赖学校资源、课程行政安排或后续决策，尚未冻结。

## 2. 已知条件与设计假设

### 2.1 已知条件

1. 一次实验课排课时长为 3 小时；
2. 阶段一的必要讲解和完整示范应在 1 小时内结束；
3. 课堂结束后开放约一周的在线验收窗口；
4. 学生应能只依靠实验文档和 Starter Kit 完成实验；
5. 学生需要在教学方限定范围内作出真实工程决策；
6. 本阶段不以模型效果或推理性能排名为主要目标；
7. 阶段一成果必须能够被阶段二的 AI Coding 工具使用；
8. 国产算力服务器数量、架构、隔离方式和可用软件栈尚未确定。

### 2.2 平台无关假设

本规格不预设具体芯片、模型或推理框架，但假设最终环境能够提供：

- 教学方可控制的国产算力资源；
- 学生之间基本隔离的运行空间；
- 预置或校内可快速访问的模型权重；
- 教学方可执行自动评测任务的 Runner；
- 教学方可读取设备、进程、端口和网络信息的环境探针；
- 从评测器访问学生模型服务的网络路径。

如果实际平台无法满足其中某项，课程团队必须在开放实验前制定等价证据或降级方案。

## 3. 实验定位

阶段一是一次受约束的模型服务交付实验。学生不是只要“运行过模型”，而是要交付一个：

- 部署在指定国产算力平台上；
- 使用允许范围内的国产大模型；
- 能由标准命令启动、停止和重新启动；
- 符合课程统一 API；
- 能被自动化系统从外部验证；
- 能在阶段二被稳定引用的模型服务。

本阶段的核心问题是：

> 学生能否在给定平台约束下，将国产大模型转化为可复现、可调用、可验证的软件服务？

## 4. 学习目标与非目标

### 4.1 学习目标

完成本阶段后，学生应能：

1. 识别硬件、驱动、运行时、推理框架、模型格式和模型服务之间的依赖；
2. 根据兼容矩阵选择合适的模型部署方案；
3. 使用配置和脚本复现模型服务；
4. 将推理框架适配为统一的服务 API；
5. 使用公开测试诊断接口、生命周期和稳定性问题；
6. 理解自动评测能够证明和不能证明的内容；
7. 将阶段一服务作为后续 AI Coding 工具的模型后端。

### 4.2 非目标

本阶段不主要考察：

- 从零安装或修复底层设备驱动；
- 从公共网络下载大型模型；
- 从源码编译复杂推理框架；
- 训练、微调或改进模型能力；
- 极限吞吐、最低延迟或跨组性能排名；
- 通用云平台运维；
- 对任意模型和任意框架的无约束兼容。

## 5. 角色与责任边界

### 5.1 课程团队在开放实验前的责任

课程团队必须准备：

1. **实验环境**：驱动、运行时、账号或容器、资源隔离和网络策略；
2. **模型注册表**：允许的模型、版本、路径、许可证说明和资源要求；
3. **兼容矩阵**：模型、推理框架、精度与硬件的已验证组合；
4. **黄金路径**：至少一条从干净环境到正式评测通过的参考路线；
5. **内部参考实现**：用于回归验证文档、平台和评测器；
6. **Starter Kit**：目录骨架、配置骨架、生命周期脚本骨架和适配器骨架；
7. **公开测试**：学生可不限次数运行的本地或远程测试；
8. **正式评测系统**：提交、调度、执行、反馈、留档和凭证签发；
9. **实验文档**：不依赖额外口头信息即可完成黄金路径；
10. **运维手册**：基础设施检查、故障分类、清理和恢复流程。

课程团队不得把未验证的模型—框架组合标记为基础路线。

### 5.2 学生的责任

学生必须：

1. 阅读任务、自由度、接口和通过标准；
2. 检查分配环境并保存必要诊断结果；
3. 在允许范围内选择模型、推理后端和部署参数；
4. 完成部署清单、生命周期脚本和必要的接口适配；
5. 确保服务能启动、停止、重启和处理规定请求；
6. 使用公开测试自查；
7. 以 Git commit 为单位提交正式评测；
8. 根据结构化反馈修改并重新提交；
9. 在截止时间前获得有效的阶段一凭证；
10. 不调用外部模型 API，不绕过课程指定模型链路。

学生不负责修复教学方驱动、模型文件、Runner 或调度系统故障。

### 5.3 实验开放后课程团队的责任

课程团队必须：

- 进行不超过约 1 小时的任务介绍和完整示范；
- 保证课堂演示严格按照公开文档执行；
- 维护服务器、Runner、模型文件和评测队列；
- 区分学生失败与基础设施失败；
- 为基础设施失败提供不计次数的重新评测；
- 把普遍问题优先修正到文档、Starter Kit 或公开测试中；
- 处理无法自动诊断的边缘情况和评测争议；
- 在截止后冻结最终通过记录并签发凭证。

助教不应长期通过私聊提供文档中不存在的“秘密步骤”。如果某条信息对完成实验是必要的，它必须进入公开文档。

## 6. 学生自由度

### 6.1 教学方固定内容

以下内容为了公平和自动化验收而固定：

- 国产算力平台和资源边界；
- 允许的模型注册表；
- 允许或明确支持的推理后端范围；
- 服务 API；
- 生命周期命令；
- 提交目录和部署清单 Schema；
- 端口、模型路径和认证信息的注入方式；
- 公开测试和正式评测协议；
- 禁止外部模型 API 转发；
- 阶段一凭证格式；
- 阶段二引用部署身份的方式。

### 6.2 学生受约束选择

学生应在兼容矩阵允许范围内选择：

- 国产模型及允许的规格；
- 推理框架；
- 精度或量化方案；
- 上下文长度；
- 批处理和并发参数；
- 单设备或允许的并行策略；
- 是否基于课程适配器骨架实现；
- 必要的缓存、日志和错误处理方式。

### 6.3 学生完全自由内容

学生可以自主决定：

- 部署代码内部结构；
- 辅助脚本和诊断工具；
- 配置拆分方式；
- 监控与日志的补充实现；
- 额外本地测试；
- 资源约束内的性能优化；
- README 的组织和表达方式。

### 6.4 基础路线与探索路线

课程应提供两类路线：

- **基础路线**：课程团队验证过的模型与框架组合，保证存在完整黄金路径；
- **探索路线**：允许改变模型、量化方式或推理后端，但仍遵循相同交付协议。

探索路线不能改变必选通过标准。探索失败的学生应能在验收窗口内退回基础路线。

## 7. 实验成果

每个学生或小组必须交付以下成果。组队方式当前待定。

### 7.1 可访问的模型服务

服务必须：

- 在正式评测时可由评测器访问；
- 提供健康检查、服务信息和对话补全接口；
- 支持非流式和流式生成；
- 使用临时认证凭据；
- 实际调用课程允许的本地模型。

### 7.2 可复现部署包

建议目录基线：

```text
stage-1/
├── ldsdt.yaml
├── ldsdt.sh
├── src/
├── config/
├── dependency-manifest
├── README.md
└── .gitignore
```

部署包必须由不可变 Git commit 标识，且不得包含模型权重和秘密信息。

### 7.3 自动评测记录

每次正式提交产生：

- `evaluation_run_id`；
- 提交时间；
- commit SHA；
- 测试结果；
- 平台证据引用；
- 结构化失败反馈；
- 最终状态。

### 7.4 阶段一部署凭证

通过后由课程系统签发：

- `deployment_id`；
- 团队或学生身份；
- commit 和配置摘要；
- 模型注册表 ID；
- 平台证明引用；
- 评测运行 ID；
- 课程签名。

凭证不得包含长期 API Key，也不应绑定不可变的服务器 IP。`deployment_id` 是阶段二引用的逻辑身份。

## 8. 课堂与一周验收流程

### 8.1 课堂目标

课堂目标不是讲授所有操作细节，而是：

- 建立实验整体认识；
- 完整演示一次文档中的黄金路径；
- 展示最终结果和通过标准；
- 展示公开测试、正式提交和失败反馈；
- 说明阶段一与阶段二的关系。

### 8.2 建议的一小时安排

| 时间       | 内容                                 |
| ---------- | ------------------------------------ |
| 0–10 分钟  | 实验目标、交付物、自由度和阶段关联   |
| 10–35 分钟 | 从干净环境完整部署基础路线           |
| 35–45 分钟 | 公开测试及一到两个典型失败示范       |
| 45–55 分钟 | 正式提交、状态查询和反馈解读         |
| 55–60 分钟 | 截止时间、重试政策和基础设施故障处理 |

剩余排课时间可以作为自愿现场开始和答疑时间，但学生离开课堂后仍必须能只依靠文档独立完成。

### 8.3 一周验收窗口

建议状态如下：

```text
课堂开放实验
→ 学生自主实现
→ 运行公开测试
→ 提交 commit
→ 正式评测
→ 根据反馈迭代
→ 截止前通过
→ 签发阶段一凭证
```

建议政策基线：

- 公开测试不限次数；
- 正式评测设置合理冷却时间或每日次数上限；
- 相同 commit 不重复执行相同正式评测；
- `INFRA_ERROR` 不消耗学生次数；
- 通过凭证绑定具体 commit；
- 截止时采用最后一个通过版本；
- 次数、迟交和补交政策待课程行政规则确定。

## 9. 基础协议基线

本节只冻结行为，精确 JSON Schema 和 OpenAPI 文件作为下一阶段产物生成。

### 9.1 部署包协议

正式提交至少包含：

- 学生或团队 ID；
- 仓库地址；
- commit SHA；
- 资源分配 ID；
- `ldsdt.yaml` 路径。

标准生命周期命令为：

```bash
./ldsdt.sh prepare
./ldsdt.sh start
./ldsdt.sh status
./ldsdt.sh stop
```

评测器注入：

- 模型根目录；
- 模型注册表 ID；
- 服务端口；
- 临时 API Key；
- 评测运行 ID；
- 日志目录。

部署必须支持重复准备、幂等停止和停止后的重新启动。

### 9.2 模型服务 API

最低接口为：

```text
GET  /healthz
GET  /course/v1/info
POST /v1/chat/completions
```

`/v1/chat/completions` 采用 OpenAI Chat Completions API 的明确子集，必须支持：

- `system`、`user` 和 `assistant` 消息；
- `temperature`；
- `max_tokens`；
- 非流式响应；
- SSE 流式响应；
- 统一错误结构；
- `X-LDSDT-Request-ID` 回显。

除健康检查外，接口使用由评测器注入的 Bearer Token。

### 9.3 部署身份协议

通过评测后签发逻辑部署身份 `deployment_id`。阶段二必须：

- 提交阶段一签名凭证；
- 以 `deployment_id` 引用模型服务；
- 在正式评测时产生可由教学网关或平台日志观察的真实调用；
- 使用请求 ID 或等价随机挑战建立阶段二工具与阶段一服务的调用关联。

仅在配置中填写 `deployment_id`，但没有真实调用记录，不构成阶段关联。

## 10. 自动评测流程

每次正式提交形成以下状态机：

```text
SUBMITTED
→ QUEUED
→ PREPARING
→ STARTING
→ TESTING
→ PASSED | FAILED | INFRA_ERROR
```

建议评测顺序：

1. 检查仓库、commit、目录和配置；
2. 检查模型与运行时声明是否在允许范围；
3. 在隔离环境中执行 `prepare`；
4. 注入环境变量并执行 `start`；
5. 从外部轮询健康检查；
6. 执行 API 和基础推理测试；
7. 执行流式、错误和短时稳定性测试；
8. 获取平台侧进程、设备和网络证据；
9. 执行 `stop` 并确认资源释放；
10. 再次启动并执行快速回归测试；
11. 清理本次运行；
12. 生成结果，或在全部必选项通过后签发凭证。

正式评测执行学生代码，因此 Runner 必须采用低权限账号、容器或等价隔离，不得以宿主机管理员权限直接执行不受信任脚本。

## 12. 通过规则与成绩边界

### 12.1 阶段通过条件

以下类别必须全部通过：

- 提交结构；
- 配置合法性；
- 生命周期；
- 健康检查；
- 非流式推理；
- 流式推理；
- 基础错误处理；
- 短时稳定性；
- 停止和重新启动；
- 国产算力平台证明；
- 无外部模型 API 转发；
- 部署身份注册。

任何必选项失败时，不签发阶段一凭证。

### 12.2 性能指标

评测器应记录但不作为主要通过门槛：

- 模型加载时间；
- 服务就绪时间；
- 首 token 延迟；
- 输出 token 速度；
- 峰值设备内存；
- 短时吞吐。

在硬件资源不完全一致时，绝对性能不得承担大量分值。性能数据可用于学生反馈、基础设施规划、课程改进和合规的后续研究。

### 12.3 数值评分

本规格冻结“是否完成”的条件，不冻结课程最终分值。若需要形成分数，建议：

- 阶段通过构成主体分；
- 工程决策说明、部署文档和额外测试提供区分度；
- 探索路线和性能优化只提供少量附加分；
- 不因分配硬件和模型天然差异造成显著分差。

## 13. 评测证据与结论边界

### 13.1 提交物静态检查能够确认

- 提交结构和配置是否合法；
- 代码版本是否可追踪；
- 模型和运行时声明是否在允许范围；
- 基本复现材料是否存在。

它不能单独确认服务能运行或推理发生在国产算力上。

### 13.2 生命周期评测能够确认

- 指定 commit 能由统一入口部署；
- 服务不依赖一次性手工操作；
- 服务能够停止并重新启动。

它不能单独确认实际模型身份或本地算力使用情况。

### 13.3 黑盒 API 评测能够确认

- 服务可从外部访问；
- API、流式协议和错误结构符合要求；
- 服务产生非固定、与输入相关的模型输出；
- 服务达到第二阶段需要的最低稳定性。

它不能单独排除外部代理或虚假模型声明。

### 13.4 平台侧证据能够确认

- 服务运行在教学方分配环境；
- 服务进程、监听端口和国产设备活动相互对应；
- 测试请求期间发生本地推理；
- 模型来源与课程模型目录相符；
- 未观察到禁止的外部模型 API 调用。

### 13.5 组合评测后的正式结论

全部证据成立后，课程团队可以合理确认：

1. 学生交付了可复现部署包；
2. 服务使用了允许的国产模型；
3. 推理发生在指定国产算力平台；
4. 服务满足统一调用协议；
5. 服务具备阶段二需要的最低稳定性；
6. 结果绑定到确定团队、commit、环境和评测运行；
7. 该成果可以获得并使用阶段一部署身份。

自动评测不能证明代码完全由学生独立编写，也不能代替对学生理解程度的全部判断；这不属于阶段一自动验收的主要目标。

## 14. 实验文档质量标准

### 14.1 文档原则

- 实验文档是完成实验的唯一权威信息源；
- 课堂讲解不得新增关键要求；
- 演示必须严格按照公开文档执行；
- 每条命令必须给出预期结果；
- 每个关键检查点必须给出失败分支；
- 公开测试错误码必须能链接到排障章节；
- 文档、Starter Kit、Schema 和测试工具必须共同版本化。

### 14.2 学生讲义的最低结构

1. 实验目标；
2. 最终成果；
3. 自由度与禁止事项；
4. 通过标准；
5. 预计用时；
6. 环境登录与诊断；
7. 模型和推理框架选择；
8. 基础路线完整流程；
9. 学生需要完成的工程工作；
10. 生命周期协议；
11. 模型服务 API；
12. 本地公开测试；
13. 正式提交；
14. 评测反馈解释；
15. 故障排查；
16. 清理与恢复；
17. 阶段一凭证及阶段二使用方式。

### 14.3 文档验收方法

实验开放前必须进行：

1. 课程团队成员从干净环境按文档完成一次；
2. 一名未参与设计的助教或学生进行无口头帮助的盲测；
3. 根据盲测记录修正文档；
4. 用参考实现重新执行公开与正式评测。

文档通过标准为：

> 一名具备课程先修能力、但未接触该国产算力平台的学生，仅依靠文档和 Starter Kit，能够完成基础路线、通过公开测试并提交正式评测。

任何必须通过口头补充才能继续的内容，都视为文档缺陷。

## 15. 评测反馈规范

正式评测应返回测试类别、状态、稳定错误码和可操作提示，例如：

```json
{
  "run_id": "run-2026-00123",
  "status": "failed",
  "commit": "9f19d1c...",
  "results": {
    "lifecycle": "passed",
    "api_schema": "passed",
    "inference": "passed",
    "streaming": "failed",
    "restart": "not_run"
  },
  "feedback": [
    {
      "code": "STREAM_MISSING_DONE",
      "message": "The streaming response did not end with data: [DONE].",
      "documentation": "/model-deployment/week-1/#stream-missing-done"
    }
  ]
}
```

反馈必须帮助学生定位问题，但不公开全部私有输入和判定细节。

## 16. 数据留存与后续研究空间

为课程改进和潜在后续研究，评测系统可以预留以下结构化数据：

- 匿名化学生或团队 ID；
- 提交时间和 commit；
- 模型、框架与配置选择；
- 各测试状态和错误码；
- 重试次数；
- 启动与推理性能指标；
- 基础设施故障记录；
- 最终是否通过。

但必须遵循：

- 教学运行优先于研究数据收集；
- 不默认保存完整学生提示、生成内容、源代码副本或凭据；
- 教学评测数据与研究使用权限分离；
- 研究用途、知情同意、匿名化、保留期限和伦理审批另行确定；
- 数据采集失败不得影响学生正常通过实验。

## 17. 风险与降级方案

| 风险                      | 影响                 | 预防或降级方案                                 |
| ------------------------- | -------------------- | ---------------------------------------------- |
| 服务器数量不足            | 无法让服务持续在线   | 采用预约评测、按需重部署和逻辑 `deployment_id` |
| 模型加载时间过长          | 评测队列积压         | 预置权重、缓存基础环境、限制模型规模           |
| 学生共享环境相互影响      | 结果不稳定或安全问题 | 容器、低权限账号、端口与设备隔离               |
| 平台探针能力不足          | 无法强证明本地推理   | 网络隔离、Runner 证据、模型目录校验组合替代    |
| 推理具有随机性            | 私有测试偶发失败     | 低温度、多样例、结构判定和有限重试             |
| 文档与环境漂移            | 大面积失败           | 参考实现回归、版本冻结、变更记录               |
| 自动反馈过于模糊          | 助教支持负担上升     | 稳定错误码、故障树、文档锚点                   |
| 正式评测被当作测试 Oracle | 过度试探私有测试     | 公开测试充分、相同 commit 去重、合理冷却时间   |
| 学生脚本破坏宿主环境      | 安全和可用性风险     | 隔离执行、无特权、资源限制、评测后清理         |

## 18. 尚未冻结的决策

以下内容必须在硬件和课程行政条件明确后补充：

### 18.1 平台相关

- 国产算力设备型号和数量；
- 单组可用设备数量和显存；
- 容器、虚拟环境或账号隔离方式；
- 驱动、工具链和推理运行时；
- 模型权重存储与访问方式；
- 学生服务网络可见范围；
- 是否允许访问公网软件源；
- 服务是否在阶段间持续在线。

### 18.2 教学组织相关

- 单人或组队，以及每组人数；
- 阶段一具体分值；
- 正式评测每日次数或冷却时间；
- 截止、迟交、补交和特殊情况政策；
- 探索路线的附加分；
- 是否要求简短工程决策说明。

### 18.3 评测阈值相关

- 最大准备时间；
- 最大启动时间；
- 单请求超时；
- 连续请求和并发数量；
- 最大上下文长度；
- 资源占用上限；
- 平台探针可以提供的具体证据；
- 外部网络限制和检测方式。

## 19. 开放实验前的完成定义

只有以下条件全部满足，阶段一才能面向学生开放：

- [ ] 实际平台和资源分配方式已确定；
- [ ] 模型注册表和兼容矩阵已发布；
- [ ] 至少一条基础路线在干净环境中跑通；
- [ ] 内部参考实现通过全部正式测试；
- [ ] Starter Kit 已完成；
- [ ] 部署清单 JSON Schema 已冻结；
- [ ] 模型服务 OpenAPI 已冻结；
- [ ] 公开测试可由学生独立运行；
- [ ] 正式评测状态机和反馈可用；
- [ ] Runner 采用隔离和低权限执行；
- [ ] 平台侧证明方案已经验证；
- [ ] 学生实验文档通过无口头帮助盲测；
- [ ] 课堂一小时演示完成彩排；
- [ ] 基础设施故障处理和延期规则已确定；
- [ ] 阶段一凭证能被阶段二解析。

## 20. 本规格之后的产物顺序

本规格评审通过后，按以下顺序继续：

1. 编写机器可读协议：部署清单 Schema、OpenAPI、评测结果 Schema、凭证 Schema；
2. 编写自动测试目录：固定测试 ID、公开性、输入类型、判定和反馈错误码；
3. 建立学生实验讲义骨架，并把平台未知内容标记为占位项；
4. 开发 Starter Kit 和公开测试 MVP；
5. 设计正式评测器、Runner 与平台探针；
6. 在实际硬件确定后完成模型注册表、兼容矩阵和黄金路径；
7. 进行内部回归和无口头帮助盲测；
8. 发布学生讲义和第一阶段实验。

其中，下一项应优先完成的是机器可读协议，因为它是学生文档、Starter Kit、公开测试和正式评测器的共同依赖。
